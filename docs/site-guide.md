# How this website is built — and how to do the same for your own projects

The Cinewright site (<https://msmahdinejad.github.io/cinewright/>) is **plain HTML, CSS and JavaScript**: no framework, no bundler, no build step, no dependencies. That is deliberate — it can never "break on npm update", any agent or human can edit it, and GitHub hosts it for free.

## 1 · What is in `docs/`

```text
docs/
├─ index.html                  the whole page (English + Persian side by side: <span lang="en">…</span><span lang="fa">…</span>)
├─ assets/
│  ├─ css/site.css             design tokens, layout, animations (logical properties → RTL works for free)
│  ├─ js/hero.js               the WebGL aurora behind the headline (one fragment shader)
│  ├─ js/live.js               the live engine demo + scrubber (drives an iframe by calling renderFrame(t))
│  ├─ js/site.js               everything else: i18n, video manager, the with/without players, atlas explorer, gallery, charts…
│  ├─ data/media.plan.json     THE SOURCE OF TRUTH for every film on the site (what, which agent, which prompt, how to encode)
│  ├─ data/media.json          GENERATED by tools/make-assets.mjs from the plan (paths, sizes, durations)
│  ├─ data/atlas.json          the technique catalogue as data — GENERATED by tools/gen-docs.mjs
│  ├─ benchmark/summary.json   benchmark results as data — GENERATED by benchmark/report.mjs
│  ├─ video/<section>/*.mp4    web films (H.264, +faststart) · img/<section>/*.jpg posters · anim/*.webp README previews
│  └─ fonts/                   the fonts, self-hosted (no Google Fonts request, works offline)
└─ demo/                       the real engine: lib/, fonts/, showreel.html, cinema.html, *.m4a — GENERATED by tools/build-demo.mjs
```

The important idea: **the site shows the product, generated by the product.** Every film is a real render, the atlas explorer reads the real catalogue, the benchmark bars read the real result files, and the "live" demo is the real engine. When the project changes, you re-run a script and the site follows. Nothing is a screenshot someone has to keep up to date.

## 2 · Media: films first (and never the same clip twice)

Version 2.2 replaced low-quality animated WebPs with real `<video>`s. The pipeline is one command:

```bash
node tools/make-assets.mjs reels          # render the atlas technique reels (960×540, 30 fps) from the skill's own recipes
node tools/make-assets.mjs build          # plan → docs/assets/video/<section>/<id>.mp4 + poster JPGs + media.json
node tools/make-assets.mjs readme         # animated WebP previews for the README (docs/assets/anim)
node tools/make-assets.mjs blocks         # fill the README gallery blocks (README.md, README.fa.md) from the same plan
node tools/make-assets.mjs release        # copy every source film to benchmark/.work/release/<name>.mp4 — the files to attach to a GitHub release
node tools/make-assets.mjs check          # every file exists, no excerpt is used twice, total size under budget
```

`media.plan.json` lists each film once with its section (`hero`, `herocard`, `compare`, `showcase`, `reel`, `engine`), its agent, its prompt and its encoding (`w`, `crf`, `audio`, poster time). The `tasks` list names the prompts of the *proof* section; every `compare` item belongs to a `task`, a `pair` (the agent) and a `side` (`without` / `with`), points at its measured result with `metrics`, and the *with* item carries a short, honest `read` ("our read") shown under the players — including for the pairs the skill does not win. Sources are the agents' own files (`benchmark/runs/…/final.mp4` or `benchmark/samples/<name>.mp4`, published as release assets). `site.js` only reads `media.json`, so adding a film is: append to the plan, run `build`.

How the page treats video (all in `site.js`): every `<video>` is lazy (`data-src` is attached 600 px before it scrolls into view), plays only while at least 35 % visible, at most five play at once, and everything pauses when the tab is hidden; `prefers-reduced-motion` shows posters only. The **proof** section is different on purpose: its players have native controls and sound (`preload="metadata"`), a "play both in sync" button and a switch that decides which side you hear.

## 3 · English and Persian, without making either a second-class citizen

Every string exists twice (`lang="en"` / `lang="fa"`); one CSS rule hides the inactive language, `dir` flips on `<html>`, fonts switch per language. Content that belongs to one language only gets the class `fa-only` (hidden in English) — the Persian section and the Persian films appear **only** in the Persian view; the English view is general. Media items carry `lang: "fa"` and the gallery filters them.

## 4 · How it is hosted (GitHub Pages, ~2 minutes)

1. Put the site in a folder (here `docs/`) and commit it.
2. Turn Pages on **with the "GitHub Actions" source** (so a workflow, not a branch, publishes it):
   ```bash
   gh api -X POST repos/OWNER/REPO/pages -f build_type=workflow
   ```
3. Add [`.github/workflows/pages.yml`](../.github/workflows/pages.yml): check out, `actions/configure-pages`, `actions/upload-pages-artifact` with `path: docs`, `actions/deploy-pages`. Push to `main` — the site is live at `https://OWNER.github.io/REPO/`.
4. Put the URL in the repository's *About → Website* (`gh repo edit --homepage URL`) and in the README.

Gotchas that bit us: use **relative** URLs (`assets/…`, not `/assets/…`) because a project site lives under `/REPO/`; renaming the repository changes the URL; `overflow-x: clip` on sections stops decorative blurred shapes from creating a horizontal scrollbar; GitHub release assets are served as downloads, not for inline playback — ship the web MP4s inside `docs/`.

## 5 · Techniques used (all in plain CSS/JS — copy what you like)

| effect | where | how |
|---|---|---|
| WebGL aurora hero | `hero.js` | a single fragment shader (domain-warped fbm noise + stars + pointer "lens"), rendered at ~60 % resolution, paused off-screen/hidden, adaptive resolution if frames get slow, CSS gradient fallback without WebGL / with reduced motion |
| Live engine demo | `live.js` | an `<iframe>` with the project's own page; the parent calls `iframe.contentWindow.renderFrame(t)` from `requestAnimationFrame` and plays the soundtrack with `<audio>`; the scrubber is a pointer-captured div with real frames as its background |
| With/without players | `site.js` | two native `<video controls>` per agent, a "play both" button that restarts both, and a mute switch deciding which side is audible; metrics bars built from the committed result JSON |
| Kinetic headline | `site.js` `splitWords` | text split into **words** (never letters — keeps Persian joined) with staggered CSS animation delays |
| Reveal on scroll, counters, nav highlight | `site.js` | one `IntersectionObserver` each |
| Scroll-linked outline text bands | `.band` | `transform: translateX()` computed from the element's position in the viewport |
| Pointer effects | `site.js` | cursor glow, magnetic buttons, 3-D tilt and spotlight borders set CSS variables from `pointermove`; all disabled on touch and with `prefers-reduced-motion` |
| Sticky storytelling | `#layers` | `position: sticky` monitor + `IntersectionObserver` on the steps; terminals "type" real captured output |
| Atlas explorer | `site.js` `initAtlas` | fetches `atlas.json`, scores entries per query word (id/title/tags/text), highlights matches, filter chips, "copy command"; the reels above it are real atlas recipes rendered to video |
| Footer wordmark | `#bw` | variable-font weight (`font-variation-settings: "wght"`) driven by pointer distance per letter |

## 6 · Checking it with a real GPU

Screenshots with WebGL need a real browser context. This repository ships a tiny tool (it reuses the skill's headless Chrome):

```bash
python -m http.server 8765 --directory docs &
node tools/shot.mjs http://localhost:8765/index.html --w 1440 --h 900 --sel "#top,#results,#showcase" --wait 4000
node tools/shot.mjs http://localhost:8765/index.html --w 390 --h 844 --dpr 2 --mobile --scroll 0,900   # phone
```

It prints console errors and the page's horizontal overflow (`sw` must equal `cw`).

## 7 · One command for another project

`tools/new-site.mjs` turns a small JSON file into a site like this one (WebGL hero, kinetic headline, rotating words, feature cards, how-it-works, install tabs with copy buttons, FAQ, English/Persian) plus the Pages workflow:

```bash
cp site-template/site.config.example.json my-project.json        # edit: name, repo, headline, features, install commands, colours…
node tools/new-site.mjs my-project.json --out ../my-project/docs  # writes index.html, assets/, 404.html and .github/workflows/pages.yml
cd ../my-project && git add . && git commit -m "Add website" && git push
gh api -X POST repos/OWNER/my-project/pages -f build_type=workflow   # once
```

The example config is a made-up app ("Pocketwise"). Strings can be plain text or `{ "en": "…", "fa": "…" }` (drop `fa` and `languages: ["en"]` for a single-language site); `*word*` in the headline gets the gradient. Add your own films by editing the generated `index.html` — it is ordinary HTML — or lift the video manager and the media-plan idea from `site.js`.

## 8 · Do the same by hand — a checklist

1. **Decide what the project's "live proof" is** (a demo, a playground, real output, a chart of real results) and generate it with a script, not by hand.
2. **Copy** `docs/index.html`, `assets/css/site.css`, `assets/js/site.js` and strip what you do not need (keep: tokens, nav, reveal, install tabs, footer).
3. **Replace** the copy, colours (`:root` tokens at the top of the CSS) and links.
4. **Make assets from the project itself** — and make them *good*: web MP4s (`ffmpeg -c:v libx264 -preset slow -crf 22 -movflags +faststart`) with a poster each; animated WebP only for places that cannot play video (GitHub READMEs): `-vf "fps=15,scale=720:-1" -c:v libwebp_anim -quality 72`.
5. **Add the Pages workflow** (section 4) and enable Pages.
6. **Add a CI check** that the generated files are up to date (`node tools/gen-docs.mjs --check`, `node benchmark/report.mjs --check`, `node tools/make-assets.mjs check`) so the site cannot drift from the repository.
7. Test on a phone-sized viewport and with `prefers-reduced-motion`.

### A prompt that makes an agent do it for you

```text
Build a GitHub Pages site for this repository in /docs: plain HTML/CSS/JS, no framework or build step, dark cinematic design,
fully responsive, respects prefers-reduced-motion. Sections: hero with a short headline and a one-line install command that
types itself, a showcase of real output generated from this project (video with poster, lazy-loaded, played only when visible —
not hand-made screenshots), how it works, install tabs with copy buttons, FAQ, footer. Put generator scripts in /tools so the
site stays in sync with the project. Add .github/workflows/pages.yml (actions/upload-pages-artifact + deploy-pages), enable
Pages with `gh api -X POST repos/OWNER/REPO/pages -f build_type=workflow`, then screenshot desktop and mobile with a headless
browser and fix anything that overflows or looks broken. Use /docs/site-guide.md in the Cinewright repo as the reference for structure.
```
